# 뛸까말까

**지금 뛰면 탈 수 있을까?**

승강장까지 걸리는 시간과 서울 지하철 실시간 도착 정보를 견줘 「걸어도 되나, 뛰어야 하나」를 알려 주는 모바일 웹앱.

**배포 주소**: https://run-or-not.vercel.app

> 서울시 실시간 도착 API는 인증키 하나에 하루 호출 한도가 있어서, 한도를 넘으면 「불러오지 못했어요」나 「도착 정보를 못 받고 있어요」 화면이 보일 수 있다.

Next.js 16 (App Router) · React 19 · TypeScript · TanStack Query · Zustand (persist) · Tailwind CSS v4 · Vitest

## 화면 흐름

1. **역 찾기** (`/`) — 역 이름으로 찾거나, 최근 본 역(5개까지)을 누르거나, 「내 위치로 찾기」로 2km 안의 가까운 역 3개를 본다.
2. **승강장까지 몇 분?** (`/station/[id]`) — 「내 위치로 계산하기」를 누르거나 3 · 5 · 7 · 10분 가운데 직접 고른다. 판정 화면의 시트에서 30초씩 바꿀 수 있다 (30초~30분).
3. **판정** — 탈 수 있는 가장 빠른 열차를 기준으로 아래 6가지 가운데 하나를 보여 준다. 역명판 양옆의 역을 누르면 방면이 바뀐다 (`?dir=up|down`).
4. **설정** (`/settings`) — 걷기 · 뛰기 속도, 역 안 이동 시간, 여유 시간을 바꾼다.

| 판정 | 조건 (남은 시간 = 열차가 도착할 때까지) |
|---|---|
| 천천히 걸어요 | 걸어서 승강장에 도착한 뒤에도 180초 이상 남는다 |
| 걸어도 돼요 | 걸어서 도착하고 여유(기본 30초)가 남는다 |
| 지금 뛰어요! | 걸으면 여유가 없지만, 뛰면 도착한 뒤 20초 이상 남는다 |
| 빨리 뛰어봐요! | 뛰어서 도착한 뒤 남는 시간이 −20초 이상 +20초 미만 (아슬아슬) |
| 탈 열차가 아직 안 보여요 | 지금 보이는 열차는 뛰어도 모두 못 탄다 |
| 열차가 없어요 | 그 방면에 보이는 열차가 0대 |

기본값은 걷기 4.5km/h · 뛰기 9.0km/h · 역 안 이동 60초 · 여유 30초. 직접 고른 값은 **승강장까지 걷는 총 시간**이고, 그중 역 안 이동 시간은 뛰어도 줄지 않는다고 본다 (5분을 고르면 「걸으면 5분 · 뛰면 3분」). 판정은 [src/lib/verdict.ts](src/lib/verdict.ts), 경계값 테스트는 [src/lib/verdict.test.ts](src/lib/verdict.test.ts).

## 실행 방법

Node.js 20.9 이상이 필요하다.

```bash
cp .env.example .env.local   # SEOUL_API_KEY= , TMAP_APP_KEY= 뒤에 키를 넣는다
npm i
npm run dev                  # http://localhost:3000
npm test                     # Vitest (한 번만 돌리려면 npx vitest run)
```

- `SEOUL_API_KEY` — [서울 열린데이터광장](https://data.seoul.go.kr)의 「실시간 지하철 인증키」. 없으면 역 화면이 「불러오지 못했어요」로 끝난다.
- `TMAP_APP_KEY` — [SK open API](https://openapi.sk.com)의 T맵 보행자 경로 키. 없어도 앱은 돈다: 걷는 거리를 직선거리 × 1.3으로 어림하고 숫자 앞에 「약」을 붙인다.
- 두 키 모두 서버에서만 읽으므로 `NEXT_PUBLIC_`을 붙이지 않는다.
- 위치 기능은 HTTPS나 `localhost`에서만 켜진다. 같은 와이파이의 휴대폰으로 개발 서버를 열 때는 `.env.local`의 `DEV_ORIGIN`에 컴퓨터 IP를 넣는데([next.config.ts](next.config.ts)), 이때 주소가 `http://`라 위치는 「쓸 수 없어요」로 보인다.
- `http://localhost:3000/preview`에서 모든 화면 상태를 가짜 데이터로 볼 수 있다 (배포 주소에서는 404).
- 역 화면은 탭 하나당 20초마다 서울시 API를 부른다. 개발 중에는 역 화면 탭을 오래 열어 두지 않는다 (숨은 탭은 주기 요청이 멈춘다).

## UI는 Claude Code, 상태 · 로직은 직접 — 경계는 `src/types/ui.ts`

화면 모양(색 · 크기 · 문구 · 상태별 그림)을 먼저 문서로 정한 뒤, 화면은 Claude Code에 **상태 없는 컴포넌트**로 맡기고 상태와 로직은 직접 짰다. 둘을 나누는 경계는 props 타입 파일 [src/types/ui.ts](src/types/ui.ts) 하나다. `src/ui/` 아래 컴포넌트는 이 타입대로 props만 받아 그리고(`useState` · `useEffect` · 스토어 · `fetch` · `Date.now()`를 쓰지 않는다), 페이지(`src/app/`)가 훅 · 스토어 · 순수 함수(`src/hooks/` · `src/stores/` · `src/lib/`)로 값을 만들어 넘긴다. 어느 쪽에 둘지는 「이 값이 맞는지 테스트로 확인할 수 있는가」로 갈랐다 — 판정, 20초 · 180초 · 60초 · 120초 비교, 새로고침 막기, 걷는 시간 계산은 로직이고, 색 · 크기 · 문구 · 시트가 올라오는 전환은 UI다 (「N분 N초」 같은 표시 형식만 UI가 맡고 테스트도 UI 쪽에 있다). 검토는 만든 쪽과 다른 도구가 했다: Claude Code가 만든 UI는 GPT(Codex)가 디자인 문서와 견주고, 직접 짠 로직은 Claude Code가 고친 코드 없이 문제 위치와 힌트만 적었다. 예외로 역명판 양옆 역 데이터를 만드는 부분([scripts/build-stations.ts](scripts/build-stations.ts)의 다음 역)과 내 위치에서 걷는 거리를 계산하는 부분([src/lib/walking.ts](src/lib/walking.ts) · [src/lib/walk-state.ts](src/lib/walk-state.ts))은 로직이지만 Claude Code가 썼다.

## 동기
아침에 급한 상황에서 지도 어플을 통해 검색해서 열차 확인 후 내 남은 거리를 생각하며 뛸지 말지 결정하기 불편했다. 매일 같은 상황인데 그냥 켜자마자 확인할 수는 없을까? 에서 시작되었다.

## 설계 결정
- **Next.js (App Router)**: 서울시 실시간 지하철 도착정보 API는 `http://` 주소라 HTTPS로 배포한 페이지에서 브라우저가 직접 부를 수 없고(mixed content), 인증키도 브라우저에 보이면 안 된다. 그래서 서버에서 대신 부르는 **Route Handler 프록시**가 필요했고, 화면과 서버 코드를 한 프로젝트에 둘 수 있는 Next.js를 골랐다. 페이지를 SSR해야 해서 고른 것은 아니다. 빌드 결과 역 찾기(`/`)와 설정(`/settings`)은 정적(○), 역 화면(`/station/[id]`)은 요청마다 렌더(ƒ)이고, 도착 정보와 걷는 거리는 브라우저가 프록시를 불러 받는다.
  - `GET /api/arrivals?id=<역 id>` — 정상 200 · 운행 없음도 빈 배열 200 · 모르는 역 404 · 서울시 API 실패 502. 화면은 이 차이로 「열차가 없어요」와 「불러오지 못했어요」를 나눈다.
  - `POST /api/walking` — T맵 보행자 경로의 총거리와 횡단보도 위치. 200 · 본문이 틀리면 400 · 모르는 역 404 · T맵 실패 502(화면은 어림값을 쓴다). 좌표는 서버 로그에 남기지 않는다.
- **TanStack Query**: 20초마다 도착 정보가 클라이언트 측에 갱신되어야 하는데 setInterval로 router.refresh()를 하면 도착 정보뿐만 아니라 서버 컴포넌트 전체를 다시 렌더링해야 해서 무겁다. 또한 여러 상태와 재요청 등을 직접 관리하려면 복잡도가 올라간다. → 주기 요청(20초), 실패 시 재시도 1회, 오프라인이면 요청 멈춤(`paused`), 화면 복귀·재연결 때 다시 요청을 라이브러리 동작으로 쓴다. 걷는 거리는 「어느 역까지, 어디서」가 같으면 다시 묻지 않는다 (`staleTime: Infinity`).
- **어느 화면을 보일지는 순수 함수 하나로**: 로딩 → 「승강장까지 몇 분?」 → 오프라인 → 불러오기 실패 → 판정 멈춤 → 열차 없음 → 판정 순서로 고른다 (`pickScreen`, [src/lib/screen.ts](src/lib/screen.ts)). 첫 요청이 실패했을 때만 오류 화면이고, 받아 둔 정보가 있으면 판정을 유지한다.
- **Zustand (persist)**: 설정과 최근 본 역은 localStorage에, 하단 「판정」 탭이 돌아갈 마지막 역은 sessionStorage에 둔다. 서버 HTML과 어긋나지 않게(hydration) 저장값 복원은 화면이 뜬 뒤에 한다. 승강장까지 걸리는 시간은 **저장하지 않는다** — 같은 역이라도 늘 같은 곳에서 여는 게 아니라서, 그 역 화면에 있는 동안만 유지한다.

## 문제 해결

### 도착 예측이 응답마다 늦어짐 → 「값이 바뀐 첫 응답」에서 도착 시각 고정
서울시 API의 `barvlDt`(도착까지 남은 초)는 열차가 같은 구간에 있는 동안 같은 값으로 머무는 경우가 많다. 그런데 `recptnDt`(정보 생성 시각)는 21~27초마다 새로 찍힌다. 그래서 흔히 쓰는 `recptnDt + barvlDt`로 계산하면 응답이 올 때마다 예상 도착 시각이 뒤로 밀린다 → 예측이 계속 늦어짐.

- 같은 위치에서 `barvlDt`가 그대로인 비율: 1·3·4·9호선 100%, 2·5·6·7호선 61~71%. 우이신설선만 실제로 줄어드는 값이었다 (10/29 측정, 요약 기준)
- 예: 고속터미널 3호선 3231 열차는 「6분 30초 후」가 응답 8번 동안 그대로였고, 그동안 `recptnDt + barvlDt`의 오차는 약 +3초 → 약 +2분 28초로 밀렸다

→ **같은 열차의 `barvlDt`가 새 값으로 바뀐 첫 응답에서 도착 시각을 계산해 고정하고, 값이 그대로면 고정한 시각을 유지한다** (`anchorArrivals`, [src/lib/arrivals.ts](src/lib/arrivals.ts)). 우이신설선처럼 매번 바뀌는 노선은 저절로 매 응답 기준이 된다.
→ 도착 4분 전~도착 구간의 ±30초 적중률이 **47% → 78%** (2026-10-29 측정, 요약 기준. 정의와 조건은 아래 「측정 방법」). 평균 내기 같은 다른 방법은 68~75%로 이 규칙보다 낮았다 (측정, 요약 기준).

### 앱을 막 열었을 때는 고정할 근거가 없음 → 노선 보정값
값이 바뀌는 걸 아직 못 봤으니 고정할 수 없다 → 처음 본 열차는 노선 보정값(`LINE_OFFSET_SEC`, 같은 날 데이터에서 노선별 `recptnDt + barvlDt − 실제 도착`의 중앙값, 예: 3호선 +43초)을 빼서 쓴다 → 이 구간 적중률 62% (측정, 요약 기준). 남은 한계는 아래 「현재 한계」.

### 받은 정보가 오래되면 판정이 틀림 → 60초에 알리고 120초에 멈춤
자동 갱신이 실패해도 받아 둔 정보로 판정은 계속 돌기 때문에, 마지막으로 받은 지 얼마나 됐는지를 화면이 말해야 한다. 「이번 열차」 줄 오른쪽 끝에 「방금 ↻」 · 「20초 전 ↻」을 보여 주고, **60초 이상**이면 굵은 「1분 전 정보 ↻」로, **120초 이상**이면 판정을 멈추고 「도착 정보를 못 받고 있어요 · 다시 받기」 화면으로 바꾼다. ↻를 누르면 바로 다시 받되, 받는 중이거나 받은 지 5초가 안 됐으면 요청을 보내지 않는다 (API 한도).

### 승강장까지 몇 분인지 모름 → 내 위치 + T맵, 안 되면 어림값, 그것도 안 되면 직접 고르기
- 위치 권한은 「내 위치로 계산하기」 · 「내 위치로 찾기」를 **눌렀을 때만** 묻는다. 이미 허용한 브라우저에서는 열자마자 계산한다.
- T맵 보행자 경로의 총거리를 걷기 · 뛰기 속도로 나누고, 역 안 이동 시간과 횡단보도 하나에 30초(역 앞 150m 안은 빼고)를 더한다 ([src/lib/walking.ts](src/lib/walking.ts)).
- 걷는 동안 T맵은 마지막으로 물은 곳에서 50m 넘게 움직였을 때만 다시 부르고, 그 사이는 움직인 만큼 거리에서 뺀다 (T맵 무료 한도 때문).
- 위치 정확도가 100m보다 나쁘거나 T맵이 실패하면(직선거리 × 1.3) 숫자 앞에 「약」을 붙인다.
- 권한 거부 · 시간 초과(허용 뒤 10초) · 미지원이면 안내 한 줄과 함께 직접 고르게 한다.

### 남은 시간을 주지 않는 노선·역 → 목록에서 제외
판정에는 `barvlDt`가 꼭 필요해서, 이 값을 주지 않거나 먼저 오는 열차를 건너뛰게 되는 노선·역을 뺐다 ([scripts/build-stations.ts](scripts/build-stations.ts), 근거는 [scripts/raw/README.md](scripts/raw/README.md) 「제외 근거」).

- **노선 11개** (`EXCLUDED_LINES`)
  - `barvlDt`가 늘 0인 10개: 8호선, 경의중앙선, 수인분당선, 신분당선, 경춘선, 공항철도, 서해선, 신림선, GTX-A (10/29 조사), 경강선 (10/30 조사)
  - 1호선: 서울교통공사 구간인 종로3가에서도 남은 시간이 있는 응답이 38%뿐이다. 일부만 남기면 남은 시간이 없는 열차가 먼저 와도 판정이 건너뛰므로 노선째 뺐다.
  - `barvlDt`가 0인 노선을 열차 위치(몇 번째 전역)로 추정해 보니 ±30초 적중 37%였다 (10/29에 `barvlDt`가 0이던 9개 노선의 열차로 잰 값, 요약 기준. 11개 노선 전체 값은 아니다).
- **역 46개** (`EXCLUDED_STATIONS`): 남긴 노선 중 서울 밖 구간 42개(값이 0이거나 데이터 없음)와 서울 경계 역 4개(가장 가까운 열차가 서울 밖 구간에 있으면 값이 0이라 첫 열차를 건너뜀)
- 결과: **299개 역**, 8개 노선 (2·3·4·5·6·7·9호선, 우이신설선)
