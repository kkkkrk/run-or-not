역까지 걸어서 걸리는 시간과 서울 지하철 실시간 도착 정보로 「지금 걸어가도 되나, 뛰어야 하나」를 판정하는 모바일 웹앱.

**배포 주소**: (배포 URL 넣기)

## 실행 방법

Node.js 20.9 이상이 필요하다.

```bash
cp .env.example .env.local   # .env.local의 SEOUL_API_KEY= 뒤에 인증키를 넣는다
npm i
npm run dev                  # http://localhost:3000
npm test                     # Vitest (한 번만 돌리려면 npx vitest run)
```

- 인증키는 [서울 열린데이터광장](https://data.seoul.go.kr)에서 「실시간 지하철 인증키」로 받는다. 서버에서만 읽으므로 `NEXT_PUBLIC_`을 붙이지 않는다.
- `.env.example`의 `TMAP_APP_KEY`는 지금 쓰지 않는다 (T맵 경로는 미구현).
- 역 화면은 탭 하나당 20초마다 API를 부른다. 개발 중에는 역 화면 탭을 오래 열어 두지 않는다 (숨은 탭은 주기 요청이 멈춘다).

## 동기
아침에 급한 상황에서 지도 어플을 통해 검색해서 열차 확인 후 내 남은 거리를 생각하며 뛸지 말지 결정하기 불편했다. 매일 같은 상황인데 그냥 켜자마자 확인할 수는 없을까? 에서 시작되었다.

## 설계 결정
- **Next.js (App Router)**: 서울시 실시간 지하철 도착정보 API는 `http://` 주소라 HTTPS로 배포한 페이지에서 브라우저가 직접 부를 수 없고(mixed content), 인증키도 브라우저에 보이면 안 된다. 그래서 서버에서 대신 부르는 **Route Handler 프록시**(`GET /api/arrivals?id=<역 id>`)가 필요했고, 화면과 서버 코드를 한 프로젝트에 둘 수 있는 Next.js를 골랐다. 페이지를 SSR해야 해서 고른 것은 아니다. 빌드 결과 메인(`/`)은 정적(○), 역 화면(`/station/[id]`)은 요청마다 렌더(ƒ)이고, 도착 정보는 브라우저가 이 프록시를 불러 받는다.
  - 프록시 응답: 정상 200 · 운행 없음도 빈 배열 200 · 모르는 역 404 · 서울시 API 실패 502. 화면은 이 차이로 「열차 없음」과 「불러오기 실패」를 나눈다.
- **TanStack Query**: 20초마다 도착 정보가 클라이언트 측에 갱신되어야 하는데 setInterval로 router.refresh()를 하면 도착 정보뿐만 아니라 서버 컴포넌트 전체를 다시 렌더링해야 해서 무겁다. 또한 여러 상태와 재요청 등을 직접 관리하려면 복잡도가 올라간다. → 주기 요청(20초), 실패 시 재시도 1회, 오프라인이면 요청 멈춤(`paused`), 화면 복귀·재연결 때 다시 요청을 라이브러리 동작으로 쓰고, 화면은 이 상태로 「첫 로딩 실패」·「보던 중 갱신 실패」·「오프라인」을 나눠 보여 준다.
- **Zustand (persist)**: 역별 도보 시간을 localStorage에 저장한다. 서버 HTML과 어긋나지 않게(hydration) 저장값 복원은 화면이 뜬 뒤에 한다.

## 문제 해결

### 도착 예측이 응답마다 늦어짐 → 「값이 바뀐 첫 응답」에서 도착 시각 고정
서울시 API의 `barvlDt`(도착까지 남은 초)는 열차가 같은 구간에 있는 동안 같은 값으로 머무는 경우가 많다. 그런데 `recptnDt`(정보 생성 시각)는 노선별 중앙값 21~27초마다 새로 찍힌다. 그래서 흔히 쓰는 `recptnDt + barvlDt`로 계산하면 응답이 올 때마다 예상 도착 시각이 뒤로 밀린다 → 예측이 계속 늦어짐.

- 같은 위치에서 `barvlDt`가 그대로인 비율 (10/29 연속 수집): 1·3·4·9호선 100%, 2·5·6·7호선 61~71%, 우이신설선 0% (매번 바뀜)
- 예: 고속터미널 3호선 3231 열차는 「6분 30초 후」가 응답 8번 동안 그대로였고, 그동안 `recptnDt + barvlDt`의 오차는 +2.5초 → +147.5초로 밀렸다

→ **같은 열차의 `barvlDt`가 새 값으로 바뀐 첫 응답에서 도착 시각을 계산해 고정하고, 값이 그대로면 고정한 시각을 유지한다** (`anchorArrivals`, [src/lib/arrivals.ts](src/lib/arrivals.ts)). 우이신설선처럼 매번 바뀌는 노선은 저절로 매 응답 기준이 된다.
→ 도착 4분 전~도착 구간의 ±30초 적중률이 **47% → 78%** (2026-10-29 측정, 조건은 아래 「측정 방법」). 평균 내기 같은 다른 방법은 68~75%로 이 규칙보다 낮았다 (요약 리포트 기준).

### 앱을 막 열었을 때는 고정할 근거가 없음 → 노선 보정값
값이 바뀌는 걸 아직 못 봤으니 고정할 수 없다 → 처음 본 열차는 노선 보정값(`LINE_OFFSET_SEC`, 같은 날 데이터에서 노선별 `recptnDt + barvlDt − 실제 도착`의 중앙값, 예: 3호선 +43초)을 빼서 쓴다 → 이 구간 적중률 62% (측정, 요약 기준). 남은 한계는 아래 「현재 한계」.

### 위치 허용을 안 할 수 있음 → 도보 시간 직접 입력
지금은 위치·경로를 쓰지 않는다. 역마다 걸어서 몇 분 걸리는지(1~60분 정수) 직접 입력받아 localStorage에 저장하고, 그 역을 다시 열면 그 값으로 판정한다.

### 남은 시간을 주지 않는 노선·역 → 목록에서 제외
판정에는 `barvlDt`가 꼭 필요해서, 이 값을 주지 않거나 먼저 오는 열차를 건너뛰게 되는 노선·역을 뺐다 ([scripts/build-stations.ts](scripts/build-stations.ts), 근거는 [scripts/raw/README.md](scripts/raw/README.md) 「제외 근거」).

- **노선 11개** (`EXCLUDED_LINES`)
  - `barvlDt`가 늘 0인 10개: 8호선, 경의중앙선, 수인분당선, 신분당선, 경춘선, 공항철도, 서해선, 신림선, GTX-A (10/29 조사), 경강선 (10/30 조사)
  - 1호선: 서울교통공사 구간인 종로3가에서도 남은 시간이 있는 행이 38%뿐이다. 일부만 남기면 남은 시간이 없는 열차가 먼저 와도 판정이 건너뛰므로 노선째 뺐다.
  - `barvlDt`가 0인 노선을 열차 위치(몇 번째 전역)로 추정해 보니 ±30초 적중 37%였다 (10/29에 `barvlDt`가 0이던 노선의 열차로 잰 값, 요약 기준. 11개 노선 전체 값은 아니다).
- **역 46개** (`EXCLUDED_STATIONS`): 남긴 노선 중 서울 밖 구간 42개(값이 0이거나 데이터 없음)와 서울 경계 역 4개(가장 가까운 열차가 서울 밖 구간에 있으면 값이 0이라 첫 열차를 건너뜀)
- 결과: **299개 역**, 8개 노선 (2·3·4·5·6·7·9호선, 우이신설선)

## 측정 방법 (2026-10-29)
- **언제·얼마나**: 2026-10-29(목) 15:36–16:12, 서울시 API **847회** 호출 (오류 0)
  - 노선별 1회 조사: 22개 역, 24회
  - 연속 수집: 11개 역을 20초 간격으로 역마다 약 25분, 823회
- **정답(실제 도착 시각)**: 승강장에서 직접 잰 값이 아니다. 수집한 응답에서 그 역에 「도착」·「출발」이 처음 나온 응답과 바로 앞 응답의 `recptnDt` 중간을 도착 시각으로 봤다 (진입 뒤 도착 없이 사라진 열차는 첫 「진입」 + 10초). 그래서 정답 자체가 응답 간격의 절반(약 ±10~14초)만큼 흔들린다.
- **적중**: 예측 − 정답이 ±30초 이내. 도착 4분 전~도착에 받은 응답마다 센다.
- **47% → 78%**: 남은 초를 주는 노선에서 정답을 잡은 열차 114대, 그 구간 응답 1,266개. 114대에는 나중에 노선째 뺀 1호선(종로3가) 10대가 들어 있다 (빼고 보면 51% → 80%, 아래 표). 고정은 응답 값만으로 하지만, 값이 바뀌기 전 응답에는 같은 날 데이터로 정한 노선 보정값을 뺐다.
- **62% (앱을 막 열었을 때)**: 도착 1~7분 전에 열었다고 보고 첫 응답 2개(약 40초)만 센 값. 노선 보정값은 같은 날 데이터로 정했고, 평가한 열차는 보정값 계산에서 뺐다.
- **자료**: 847회의 원본 응답 JSON은 남아 있지 않다 (수집 중 브라우저에만 있었고 분석 뒤 지움). 남은 것은 열차별 정답 목록, 노선별 집계, 예시 열차의 전체 응답 같은 요약 자료이고 저장소에는 넣지 않았다. 그래서 위 수치는 「검증」이 아니라 그날 **측정한 값(요약 기준)**이다. 47%·78%는 남은 노선별 집계로 다시 계산해도 같고, 37%·62%·68~75%는 요약 리포트에만 있는 값이다.

## 현재 한계
- **위치·T맵 경로 미구현** → 도보 시간은 역마다 직접 입력한다 (1~60분 정수). 뛰는 시간은 입력한 도보 시간에 기본 속도 비율(걷기 1.3 m/s → 뛰기 3.0 m/s)을 곱해 구하고, 둘 다 역 입구→승강장 60초를 더한다. 「걸어가요」는 30초 여유를 더 둔다. 이 기본값을 바꾸는 설정 화면은 없다.
- **남은 시간을 주지 않는 노선 제외** → 1호선을 포함한 11개 노선과 서울 밖·경계 역 46개는 검색되지 않는다. 환승역에서도 그 노선은 보이지 않는다.
- **측정은 하루, 약 35분 데이터** → 2026-10-29(목) 15:36–16:12 한 번뿐이다. 출퇴근 혼잡, 주말, 지연·사고 때는 확인하지 않았다. 노선 보정값도 이날 값이라 다른 날엔 달라질 수 있다 (10/30 17시대에는 2호선 +2초, 9호선 +30초로 크게 달랐다).
- **노선마다 효과가 다르다** → 2호선(60% → 56%)과 우이신설선(74% → 73%)은 고정 규칙으로 나아지지 않았다.
- **앱을 막 연 구간은 62%** → 값이 바뀌는 걸 보기 전이라 노선 보정값에 기댄다. 나중에 서울 전체 도착 정보를 일괄 수집 API로 저장해 두고 그 값으로 계산하는 방법을 생각하고 있다.
- **서울시 API 일일 호출 한도** → 인증키 하나를 개발·배포·모든 방문자가 나눠 쓴다. 탭 하나가 20초마다 부르면 시간당 약 180회이고, 탭·기기·방문자가 늘면 합산된다. 한도를 넘으면 오류 화면이나 「최신 정보를 못 받았어요」 안내가 보인다.
- **종점역의 출발 방향은 「열차 없음」으로 보인다** → 승강장에서 출발을 기다리는 열차는 서울시 API가 출발까지 남은 시간을 주지 않아(`barvlDt` 0) 걸러진다. 예: 3호선 오금 상행 (2026-11-09 확인).
